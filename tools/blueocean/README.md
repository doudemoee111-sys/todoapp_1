# blueocean — 軸1＋軸2 統合ツール

[提案④ 補論](../../docs/business-plan/proposal-04-cross-border-export/DROPSHIP-ANALYSIS.md) で提示した
**軸1（リサーチの向きを逆にする）** と **軸2（無在庫を需要検知センサーとして使い、当たりだけ有在庫化する）**
を1本のパイプラインに統合したツールです。

---

## なぜこの2つは「組み合わせる」必要があるのか

調査の過程で、設計を決定づける制約が見つかりました。

> **eBayの Marketplace Insights API（落札実績の取得）は、主要パートナー以外に開放されていません。**

つまり個人セラーは「何がいくらで売れたか」を外部データとして買えません。
一方、**Browse API（現在出品中の検索）は公開されており、個人でも使えます。**

| 欲しいデータ | 取得手段 | 個人が使えるか |
|---|---|---|
| 競合の出品数・価格帯 | **Browse API** | **使える** |
| 落札実績（何が売れたか） | Marketplace Insights API | **使えない** |

**軸1だけでは「競合がいない」ことは分かっても「売れる」ことは分かりません。**
競合ゼロは、需要がないから誰も出していないだけかもしれない。

ここを埋めるのが軸2です。**自分の出品の反応（閲覧・ウォッチ・販売）が、
個人が手に入れられる唯一の需要データになります。**

```
軸1  Browse APIで「競合が少ない」を判定  →  だが「売れる」かは分からない
                     ↓
              少量で出品して反応を見る
                     ↓
軸2  閲覧・ウォッチ・販売から需要を確定  →  当たりだけ有在庫化
                     ↓
              その実績が次の軸1の判定材料になる（ループ）
```

**2つは別々の施策ではなく、データの欠落を互いに埋め合う1つのループです。**
だからツールとして統合する意味があります。

## ブラウザ版 ── eBay用とShopee用の2本

インストール不要で使える版が2つあります。**市場ごとに前提が違うので、1本にまとめていません。**

| ツール | ファイル | 公開URL |
|---|---|---|
| eBay輸出用 | `web/ebay.html` | https://claude.ai/code/artifact/1798998a-3344-4dc1-a20b-452ad5075d8d |
| Shopee輸出用 | `web/shopee.html` | https://claude.ai/code/artifact/7df6808d-adcd-435f-80e2-f018c1d2bfde |

どちらも画面は**業務の順番**で4つだけです。

```
① 探す  →  ② 選ぶ  →  ③ 出す  →  ④ 追う      （＋ 設定・使い方）
```

- **① 探す** — 国内ショップの公式APIから候補を採る条件を組み立て、コマンドを出す。採れたCSVを読み込む
- **② 選ぶ** — 商品一覧が主役。仕入値を入れると送料・課金重量・仕入上限・利益率・判定が同じ行に出る（数千行対応）
- **③ 出す** — eBay用は値決めとセット販売、Shopee用は出品枠・一括出品CSV・価格差の確認
- **④ 追う** — 毎週の観測を貼ると前回比つきで次の一手が出る

### 2本に分けた理由

| | eBay用 | Shopee用 |
|---|---|---|
| 国際送料 | セラー負担（原価に乗る） | **SLSが処理。セラーは国内送料のみ** |
| 関税 | DDPでセラー負担 | **原則 購入者負担（0%）** |
| 売価の下限 | $30 | **$8** |
| 出品数 | 実質的な上限なし | **500〜1,000点（台湾は500）／無在庫は約100点** |
| ③出す の中身 | 値決め・値下げ余地・セット販売 | 枠の管理・一括出品・価格差の確認 |

この違いを1画面に同居させると、どちらの前提で計算されているのかが読めなくなります。

### 計算がずれない作り

**計算式は `web/parts/core.js` の1本にしかありません。**
両方のツールが同じファイルを取り込んでビルドされるので、片方だけ式が古い、という状態が構造的に起きません。

```bash
python web/build.py        # parts/ から ebay.html と shopee.html を組み立てる
```

Python版との一致は `tests/test_parity.py` が **node で core.js を実際に走らせて** 突き合わせています
（利益・仕入上限・送料6ケース＋失敗ケース・国内区間・値決め・為替/関税の損益分岐・返品・セット販売・判定13ケース）。
数字が1円でもずれたらテストが落ちます。

> 旧版の9タブ1枚もの（`web/index.html` / https://claude.ai/code/artifact/11f80f71-b110-4b1f-9b46-3cd62ceee330 ）
> はそのまま残してあります。抽出ワークシート・写真の貼り付けなど、新しい2本に移していない画面がそこにあります。

### 仕入上限の逆算（まずこれを触ってください）

```bash

```

```
必要な「売価 ÷ 仕入」倍率: 2.35 倍

--- 内訳 ---
  売価                30000
  手数料               -5460
  関税                -3750
  送料                -3000
  梱包                 -200
  仕入               -12000
  消費税還付              1091
  利益                 6681
  利益率               22.3%
```

重量・寸法を渡さない場合は、市場ごとの固定値（概算）が使われます。
**実運用では必ず `--weight-g` と寸法を渡してください**（次節）。

市場とセラーレベルを変えると、難易度が変わることが確認できます。

```bash
python -m blueocean.cli --market shopee_sea margin --price 200      # 1.41倍
python -m blueocean.cli --level below_standard margin --price 200   # 2.79倍
python -m blueocean.cli --no-tax-refund margin --price 200          # 免税事業者
```

### 送料：重量と寸法から出す

送料は市場ごとの固定値ではなく、**課金重量**から計算します。

```bash
python -m blueocean.cli --market ebay_us ship --weight-g 900 --length-cm 30 --width-cm 25 --height-cm 20
```

```
=== 送料見積もり（ebay_us = zone4）===
実重量 900g / 寸法 30x25x20cm

  epacket     2,915円   課金重量    900g
  ems         5,300円   課金重量    900g
  parcel      6,144円   課金重量   2500g（容積 2500g） ← 容積課金
  courier    11,313円   課金重量   3000g（容積 3000g） ← 容積課金
```

固定送料をやめた理由は2つあります。

1. **料金は重量区切りで階段状に上がる。** 950gと1,050gでは1段違います。
   梱包後に100g超えて1段上がると、その差はそのまま利益から消えます。
2. **嵩張るものは容積重量で課金される。**

   ```
   容積重量(g) = 縦cm × 横cm × 高さcm ÷ 除数 × 1000
   ```

   除数は手段ごとに違います（クーリエ 5,000／国際小包 6,000）。
   そして **EMSは容積重量を採りません（実重量のみ）。**
   このため、軽くて嵩張る荷物では **EMSがクーリエを逆転して最安になる**ことがあります。
   固定送料ではこの逆転が見えず、常に誤った手段を前提に採算を組むことになります。

`margin` にも重量・寸法を渡せます。

```bash
python -m blueocean.cli margin --price 200 --cost 12000 \
    --weight-g 400 --length-cm 20 --width-cm 15 --height-cm 10
```

```
送料: 2,299 円（epacket / 課金重量 400g）
目標利益率 20% を満たす仕入上限（税込）: 13,520 円
必要な「売価 ÷ 仕入」倍率: 2.22 倍
```

#### 料金値の扱い（重要）

既定の料金表は、**公表値として確認できた金額（アンカー）と、その間を刻み幅で内挿した推定値**が
混ざっています。推定値には見積もり時に「推定値」の警告が付きます。

**内挿値のまま仕入判断に使わないでください。**
[日本郵便の公式料金計算](https://www.post.japanpost.jp/cgi-charge/) で
実際に使う地帯・重量帯を確認し、CSVで差し替えて運用します。

```bash
python -m blueocean.cli --rates data/rates.csv ship --weight-g 900
```

```csv
zone,max_weight_g,jpy
zone3,1000,4650
zone3,2000,5900
```

差し替えれば、課金重量・階段料金・手段比較という計算構造はそのまま使えます。

#### 米国宛ての取扱い

米国宛てを選ぶと、次の警告が出ます。

> 2025年8月のデミニミス（$800免税）撤廃を受け、日本郵便は物品を含む小形包装物・国際小包・
> EMS(物品)の引受を一時停止しました。2026年4月14日以降、米国税関が認証した事業者のアプリで
> 関税を事前納付すれば、指定郵便局で引受再開。

**その手当てが済むまで、米国宛ての見積もりは UGX / FedEx / DHL で行ってください。**
提案④の試算は郵便を前提にしていたので、米国比率が高い計画ではここが効きます。

### 軸1：出品候補を判定する

```bash
python -m blueocean.cli axis1 --candidates data/candidates.sample.csv --out plan.csv
```

```
[BLUE ] 105.5  競合   2  利益率 28.2%  Konica Hexanon AR 40mm F1.8
           - 競合 2件。値下げ圧力を受けにくい
           - 需要の裏付け：近縁モデルの落札あり
[PROBE] 120.2  競合   0  利益率 29.2%  山下達郎 FOR YOU 帯付 LP
           - 競合0件だが需要の裏付けが無い。少量で反応を試す（軸2へ）
[EXCL ]   0.0  競合  41  利益率  n/a  限定フィギュア 2016年版（外箱付き）
           - 除外：容積重量 2500g（実重量 900g）が上限 2000g を超過。軽いが嵩張るため送料で採算が崩れる
[EXCL ]   0.0  競合   9  利益率  n/a  Makita cordless driver 18V with battery
           - 除外：リチウム電池内蔵で航空輸送規制

[送料の注意] 米国宛て：2025年8月のデミニミス（$800免税）撤廃を受け、日本郵便は
             物品を含む小形包装物・国際小包・EMS(物品)の引受を一時停止した。（後略）
```

**`FIG-001` の除外が、送料を重量・寸法で計算するようにした効果です。**
実重量900gは上限2,000g以内ですが、外箱込みで30×25×20cmあるため容積重量は2,500g。
実重量だけを見ていると通ってしまい、送料で利益が消えます。

判定は5種類です。

| 判定 | 意味 | 次の行動 |
|---|---|---|
| `BLUE` | 競合が少なく、需要の裏付けもある | 最優先で出品 |
| `PROBE` | 競合は少ないが需要が未確認 | **少量で出して軸2で確かめる** |
| `THIN` | 採算が目標に届かない | 見送り（仕入値が下がれば再評価） |
| `RED` | 競合過多 | 見送り |
| `EXCLUDE` | 規制品・重量超過・低単価 | 対象外 |

**競合ゼロを自動的に `BLUE` にしないのが、このツールの肝です。**
「誰も出していない＝売れない」可能性を必ず残し、`PROBE` として少量検証に回します。

### 仕入値はどこに入れるのか

**ブラウザ版は「軸1」タブの表の「仕入(円)」欄です。** 行に直接入力すると、
その場で判定と仕入上限が変わります。判定を動かせる変数は3つあり、
そのうち自分で決められるのは仕入値だけなので、ここだけは表で直に触れるようにしてあります。

| どこ | いつ使うか |
|---|---|
| 「1件だけ判定」タブの「仕入価格」 | 店頭でその1点を判定するとき |
| **「軸1」タブの表の「仕入(円)」** | **候補が複数あるとき。入力すると即座に判定が変わる** |
| 候補CSVの `cost_incl_tax_jpy` 列 | 走査の出力を読み込んでから表で埋めるのが楽です |
| 「値決め」タブの「仕入価格」 | 仕入れた後。ここからは出品価格と値下げ幅の話 |

仕入上限を超えると、その行の上限が赤字になり判定が `THIN` に落ちます。
判定カードの「↕」に**「仕入をあと◯円下げれば採算に乗る」**と出るので、
そのまま値切り交渉の目標額として使えます。

### 判定は何を基準に変わるのか

判定を動かす変数は**3つだけ**で、そのうち**自分で動かせるのは仕入値だけ**です。

| 変数 | 動かせるか | 判定への効き方 |
|---|---|---|
| **仕入値** | **自分で決められる** | 安く買えば `THIN` から抜けられる |
| 競合の出品数 | 他人が決める | 増えれば `RED` に落ちる |
| eBayの相場 | 他人が決める | 下がれば仕入上限も下がる |

これに加えて、**前提条件（為替・関税・手数料・セラーレベル・目標利益率）**と
**重量・寸法（送料を通じて）**が、全候補に同時に効きます。
候補**そのもの**が入れ替わるのは、候補CSVを差し替えたときだけです。

判定の下に、**何がどう変われば裏返るか**を1行で出します。

```
[BLUE ] 105.5  競合   2  利益率 28.2%  Konica Hexanon AR 40mm F1.8
           - 競合 2件。値下げ圧力を受けにくい
           - 需要の裏付け：近縁モデルの落札あり
           ↕ 競合があと28件増えると見送り／相場が $154 まで下がると採算割れ
           ▸ 写真で照合: https://www.ebay.com/sch/i.html?_nkw=Konica+Hexanon+AR+40mm+F1.8
```

| 判定 | 出る文言 |
|---|---|
| `BLUE` | 競合があと◯件増えると見送り／相場が $◯ まで下がると採算割れ |
| `THIN` | **仕入をあと◯円下げれば採算に乗る**（値切り交渉の目標額になります） |
| `RED` | 競合が◯件以下に減れば再評価。ただし競合数は自分では動かせない |
| `PROBE` | 需要の裏付けが取れれば BLUE。少量で出して軸2で確かめる |

「なぜこの判定か」より「**何が変われば変わるか**」のほうが行動につながる、という考え方です。

### 軸2：出品後の反応から次の一手を決める

```bash
python -m blueocean.cli axis2 --observations data/observations.sample.csv \
    --total-orders 120 --seller-cancellations 5
```

```
[PROMOTE] LENS-002   34日 / 閲覧 142 / ウォッチ  5 / 販売1
            1件 販売済み。需要が確定したので有在庫化し、ハンドリングを1〜2日に短縮する
[REPRICE] VINYL-001   22日 / 閲覧  98 / ウォッチ  0 / 販売0
            閲覧98件に対しウォッチ0。露出はあるので価格が原因
[RETITLE] REEL-001   53日 / 閲覧   6 / ウォッチ  0 / 販売0
            53日で閲覧6件。露出不足。海外バイヤーが実際に打つ語彙にタイトルを組み直す
[DROP   ] FIG-001  114日 / 閲覧  21 / ウォッチ  0 / 販売0
            114日間 無反応。出品を終了して枠を空ける

[警告] 在庫切れ率 4.2% が閾値 2% を超過。Below Standard に落ちると手数料が6ポイント
      上がり、必要な仕入倍率が 2.35倍→2.79倍に悪化する。出品数を減らすこと
```

判定の意味は次のとおりです。

| 判定 | シグナル | 意味 |
|---|---|---|
| `PROMOTE` | 販売あり／期間内にウォッチ3件以上 | **有在庫化する。当たり** |
| `REPRICE` | 閲覧は多いがウォッチ0 | 露出はある。価格が原因 |
| `RETITLE` | 30日で閲覧10件未満 | そもそも見られていない。検索語を直す（軸4） |
| `DROP` | 90日無反応 | 畳んで出品枠を空ける |
| `KEEP` | 上記以外 | 観察継続 |

**在庫切れ率の警告が最も重要です。** セラー都合キャンセルが積もると Below Standard に落ち、
落札手数料に6ポイント上乗せされます。利益率20%の前提そのものが崩れるため、
このツールは毎回この数字を出します。

## 抽出 ── 人がやる作業の、前と後を道具にする

**自動巡回はしません**（規約上の判断。上記「国内モールのAPI」参照）。
担うのは**その前後**です。

```
前   条件を決めて、開くべき検索ページのURLを組み立て、採る項目を定める
     ↓
（抽出）  人が開いて、人が採る  ← ここだけ手作業
     ↓
後   採ってきたデータを検品して、軸1に流せる形に直す
```

### ① 開くページを出す

```bash
python -m blueocean.cli extract urls \
    --keyword "Konica Hexanon AR 40mm F1.8" --category カメラ
```


### ② 採る項目 ── 定石に足りていない2つ

国内せどりの定石は **「価格安定 × セラー少ない × ランク良い × Amazon不在」**。
よくできた基準ですが、**輸出では2つ足りません。**

| ★ 項目 | なぜ効くか |
|---|---|
| **課金重量（寸法）** | 軽くて嵩張るものは実重量では課金されない。薄利だと送料が丸ごと利益を食う。**国内販売では要らないので、リサーチ項目に入っていないことがほとんど** |
| **リピート可能性** | 一点物は売れても次が無い。**Shopeeのように出品枠が限られる市場では、枠を一点物で埋めると詰む** |
| 仕入元の数 | 1箇所しか買えないと、切れた時点で終わり。無在庫では致命的 |
| 仕入価格の振れ幅 | 薄利では仕入の変動が丸ごと利益を食う |
| セットにできる括り | 同シリーズ・同ブランドでまとめられるか。束ねると送料が1回で済む |

```bash
python -m blueocean.cli extract fields          # 項目の一覧と、なぜ採るのか
python -m blueocean.cli extract sheet --out sheet.csv
python -m blueocean.cli extract sheet --out sheet.csv --minimal   # 必須だけ
```

シートには**2〜4行目に「列の意味・なぜ要るか・記入例」**を入れます。
列だけ渡されても人は埋められないので、同じファイルに理由を書きます。
残したまま埋めても、消して埋めても構いません（読み込み時に飛ばします）。

> **凡例の判定は中身ではなく位置で行っています。** 記入例の `LENS-001` は
> 実在しうるSKUで、中身だけで見分けようとすると本物のデータと区別が付きません
> （実装中に実際に消しました）。

```
=== 検品（5行）===

  要修正 6件 / 注意 5件

[要修正] LENS-001   管理番号が 1行目 と重複しています
[要修正] BAD-001    相場（約2,250円）が仕入 50,000円 を下回っています。桁か通貨を取り違えていませんか
[注意  ] BATT-001   「リチウム」を含みます。リチウム電池内蔵は航空輸送規制の対象
```

| | 見るところ |
|---|---|
| **要修正** | 必須列が空／管理番号の重複／**相場が仕入を下回る**（桁か通貨の取り違えがほとんど） |
| **注意** | 寸法が空／「また買えるか」が空／**規制に触れやすい語を含む** |

規制語（リチウム・化粧品・食品・象牙・エアガンなど）は**止めるのではなく確認を促します。**
機械が「禁止」と決めると、判断の責任の所在が曖昧になるためです。

**ブラウザ版の「抽出」タブ**でも同じことができます。
検索語を入れるとリンクが出て、シートを作り、貼って検品し、「軸1に送る」で判定の表に入ります。

## 候補リストは、どうやって作るのか

**これが最初の設計の弱点でした。** 軸1をCSVのバッチ判定として作ったので、
「手元に候補リストがある」状態を前提にしていました。
つまり**リストに無いものは永久に見つからない**。そして現実の仕入れでは、
候補リストのほうが後から出来ます。前提が逆でした。

入口を2つ足しました。

### 入口1：1件だけ、その場で判定する（`check`）

店頭やフリマアプリを見ている最中に「これは買いか」を即答するための口です。
CSVも履歴も要りません。**問い合わせた瞬間の値で判定する**ので、
バッチ実行のタイムラグがありません。

```bash
python -m blueocean.cli check \
    --title "Konica Hexanon AR 40mm F1.8" --cost 9800 \
    --weight-g 180 --length-cm 16 --width-cm 12 --height-cm 10 --demand
```

```
=== Konica Hexanon AR 40mm F1.8 ===

  判定       [BLUE]
  eBay相場   $185 / 競合 2件
  仕入上限   12,295円（税込）
  仕入 9,800円 → 採算は取れる（上限まで +2,495円）

  - 送料 2,299円（epacket / 課金重量 180g）
  - 競合 2件。値下げ圧力を受けにくい
```

`--price-usd` と `--competitors` を手で渡せば、API無しでも使えます。
**ブラウザ版の「1件だけ判定」タブも同じ計算です**（相場と競合数は手入力）。

### 入口2：キーワード空間を走査する（`scan`）

「eBayに**出ていない**型番」を先に特定し、それを国内で探しに行きます。

```bash
python -m blueocean.cli scan --keywords data/keywords.sample.txt \
    --assume-weight-g 400 --assume-length-cm 20 --assume-width-cm 15 --assume-height-cm 10 \
    --out candidates.csv
```

```
=== キーワード走査（12件 / 探す価値あり 4件）===   ※以下は抜粋
送料の仮定: 400g / 20x15x10cm

          競合      相場    仕入上限    倍率  キーワード
[空き  ]     3 $    185     12,295円   2.26倍  Konica Hexanon AR 40mm F1.8
[要検証]     0 $    230     15,970円   2.16倍  Minolta MC Rokkor 58mm F1.2
[過密  ]    41 $    410     30,672円   2.01倍  Shimano Stella 2500

--- 探す価値がある上位 ---
  Konica Hexanon AR 40mm F1.8
    予算 12,295円まで（この額を超える値札は、その場で見送れる）
```

**`予算` が実務上いちばん使う数字です。** これを持って国内を回れば、
値札を見た瞬間に「買える／買えない」が決まります。相場を調べ直して電卓を叩く手間が消えます。

`--out` を付けると**軸1の候補CSVの雛形**を書き出します。仕入値・重量・寸法は空です。
国内で現物を見つけたらそこだけ書き足して `axis1` に流せば、走査と判定が1本に繋がります。

> 雛形の行は仕入値が空なので、**判定は最良でも `PROBE` に留まります。**
> 仕入値0を「タダで買える」と解釈して `BLUE` を出すと、実体のない候補が最優先で並ぶためです。

### 入口3：ジャンルから走査する（`scan --genre`）

型番の一覧を作る前に、**ジャンルから始めたい**のが普通です。ただし
「anime figure」のような広い語を1本投げても意味がありません。数万件が出るだけで、
**自分の1点が埋もれるかどうかは分からない**からです。

そこで**ジャンルは判定ではなく展開に使います。**

```
ジャンル（アニメ・フィギュア）
    → シリーズ × 形態 の掛け合わせでクエリを生成（110本）
    → 生成したクエリを1本ずつ走査
    → 競合が薄いスライスだけが残る
```

広いクエリを1本投げるのではなく、**狭いクエリを大量に投げて薄い場所を探します。**

```bash
python -m blueocean.cli scan --list-genres
```

```
  anime_figure   アニメ・フィギュア
                 展開後 110クエリ（単品 70 / セット 40）
  vinyl          レコード（和モノ・シティポップ）
  camera_lens    オールドレンズ・フィルムカメラ
  trading_card   トレーディングカード
```

```bash
python -m blueocean.cli scan --genre anime_figure --mode set \
    --assume-weight-g 1100 --assume-length-cm 32 --assume-width-cm 24 --assume-height-cm 18
```

`--mode` は `single`（単品での出品）／`set`（まとめ売り）／`both`。
**`set` を選ぶと `figure lot` `goods bundle` `merchandise set` `job lot` を掛けた
クエリだけを走査します** ── まとめ売りの相場と競合を見るための入口です。

ジャンルごとの規制・注意も走査の時点で出します。

```
  [このジャンルの注意] 非正規品（bootleg）はeBayで禁止。仕入元の正規性を必ず確認すること
  [このジャンルの注意] 成人向けは各国の税関とeBayポリシーで問題になる。扱わない
  [このジャンルの注意] 電飾付き・電池内蔵は航空輸送規制の対象になりうる
```

`--genre-file` に JSON を渡せば独自のジャンルを足せます。

```json
{"my_genre": {"label": "自作", "bases": ["..."], "forms": ["..."],
              "set_terms": ["lot"], "cautions": ["..."]}}
```

### キーワードはどう用意するのか

ここは人間の仕事として残ります。得意ジャンルの型番表
（メーカーの製品一覧、機種リスト、レンズの型番体系）を一度作れば、それが資産になります。
100〜500行あれば毎週の走査に足ります。`data/keywords.sample.txt` が雛形です。

```
# --- オールドレンズ（国産マニュアルフォーカス） ---
Konica Hexanon AR 40mm F1.8
Nikon Ai-s 50mm F1.2
```

粒度は**型番まで**が基本です。ブランド単位だと競合数が意味を持たなくなります。

**商品は固定でも、キーワード空間は固定ではありません。** そして同じキーワードでも
競合の状況は毎週変わるので、走査は繰り返す価値があります。

### 国内モールのAPIから候補を採る（`domestic`）

以前この節には「**推奨できる手段は見つかりませんでした**」と書いていました。
そのときの判断の根拠のうち、楽天については**書き方が正確ではありませんでした。**
楽天アフィリエイトのガイドラインが禁じているのは「せどり・転売を促進する**コンテンツ**」であって、
API利用規約が仕入リサーチそのものを名指しで禁じているわけではありません。
両者を一緒くたにして「使わない」と書いたのは踏み込みすぎでした。

現在は、**利用者自身が各社に登録して発行を受けた公式APIを叩く経路**を実装しています。
巡回（スクレイピング）は一切しません。HTMLを取りに行くコードはこのパッケージに入っていません。

| 取得元 | 使えるか | 鍵 | 1クエリの上限 | 間隔 | 特徴 |
|---|---|---|---|---|---|
| 楽天市場 Ichiba Item Search API | **使う** | `RAKUTEN_APP_ID` | 30件×100ページ＝**3,000件** | **1秒に1回** | 税込/税別フラグ・**送料込みフラグ**・在庫・越境発送可フラグが返る |
| Yahoo!ショッピング 商品検索(v3) | **使う** | `YAHOO_CLIENT_ID` | 50件×20ページ＝**1,000件** | 余裕をみて0.25秒 | **JANコードが返る**ので店をまたいで同一商品を束ねられる。新品/中古も絞れる |
| Amazon PA-API 5.0 | 入れていない | — | — | — | アソシエイト審査＋一定期間内の売上実績が要る。実績が切れると止まる |
| メルカリ・ヤフオク・駿河屋 | **使わない** | — | — | — | 公開APIが無い。スクレイピングは実装しない |

```bash
python -m blueocean.cli domestic keys          # 鍵の登録状況と発行先を出す

python -m blueocean.cli domestic search \
  --source rakuten,yahoo --keyword "ねんどろいど" \
  --min-price 500 --max-price 20000 --split-price 5 --max-items 3000 \
  --domestic-shipping 600 \
  --out items.csv --candidates-out candidates.csv
```

`--dry-run` を足すと、叩かずに送るパラメータだけ確認できます。

#### この経路で必ず言うようにしてあること

**1. 取りこぼしを黙らせない。**
どちらのAPIにも「検索結果の窓」の上限があります。該当5万件でも辿れるのは3,000件です。

```
! 条件『「フィギュア」』の該当は 50,000件 だが、楽天市場のAPIは 3,000件 までしか返せない。
  **47,000件は取れていない。** 価格帯で分割して取り直すこと（--split-price）
```

`--split-price N` は価格帯を**等比で**割ります。等分（1万円ずつ）だと安い帯に商品が偏って
分割の意味がなくなるためです。

**2. 重量と寸法は、どちらのAPIも返さない。**
返らない値を0のまま流すと「軽い＝送料が安い」と読まれて判定が甘く出ます。
そこで商品名（`1kg` `500ml` など）とカテゴリから当てて埋め、**推定で埋めた候補は
`BLUE`（出せる）に上げません。**「128GB」の GB を g と読まないよう、
単位の直後に英数字が続くものは弾いています。

**3. 表示価格は原価ではない。**
楽天の `taxFlag=1` は税別表示なので10%を乗せます。`postageFlag=1` は送料別なので、
`--domestic-shipping` を指定しないと原価を安く見積もったままになります。その場合も警告を出します。

#### 規約について

各社の条件は自分で確認してから使ってください。楽天のAPIはアフィリエイト用途を前提に無償提供されており、
Yahoo!は商用利用について問い合わせ窓口が用意されています。
**自分の仕入れ判断のための価格照会**という範囲を超える使い方（データの再配布、第三者提供など）をする場合は、
事前に各社へ確認が必要です。このツールは取得結果を外部に送信しません。

なお、**楽天カードの規約は転売目的の仕入れを禁止しています**（2022年6月改定）。これはカードの話で
APIの話ではありませんが、決済手段としてそのカードを使う場合は別途効いてきます。

## Shopee専用の一括運用 ── 「数千点を出す」ではなく「枠に何を置くか」

仕入元から数千件を引いて一括出品し、価格差を定期的に見張る ──
**eBayを前提にすればその設計で正しいのですが、Shopeeでは載りません。**

| 枠 | 台湾 | 他市場 | 条件 |
|---|---|---|---|
| 新規開店時 | **500点** | 1,000点 | ここから始まる |
| Preferred Seller | 10,000点 | 10,000点 | 認定が要る |
| 実績上限 | 20,000点 | 20,000点 | 販売実績を積んで初めて届く |
| **プレオーダー（無在庫）** | **100点前後** | **100点前後** | **超えると売上の低い順に自動削除** |

**無在庫で置けるのは100点程度**で、新規開店時は全体でも500〜1,000点。
そして**枠を超えたときに何を残すかを決めるのはShopee**です。
自分で落とさなければ、機械に選ばれます。

### 出品枠の管理

```bash
python -m blueocean.cli --market shopee_tw shopee slots \
    --listed 480 --preorder-listed 130 \
    --observations data/observations.csv --candidates data/candidates.csv
```

```
=== 出品枠（Shopee 台湾 / new）===

  出品枠               480 / 500点（残り 20点）
  プレオーダー枠       130 / 100点（残り -30点）
  自動削除される数      30点  ← 自分で選ばないと機械に選ばれます

  落とす候補（軸2のDROP）     1点
  入れる候補（軸1）           5点 / 入れられるのは 21点まで
```

**入れ替え候補は、軸2の `DROP` と軸1の `BLUE`/`PROBE` を突き合わせて出します。**
枠が埋まっているなら、1つ入れるには1つ落とすしかありません。

### 価格差の定期確認

```bash
python -m blueocean.cli --market shopee_tw shopee reprice \
    --listings data/listings.csv --out out/reprice.csv
```

```
=== 価格差の確認（Shopee 台湾 / 6点）===

  いま動かすべき  2点（止める 2 / 値上げ 0）
  下げ余地あり    0点
  据え置き        4点

[止める  ] ビオレUV アクアリッチ 70ml     利益率 -33.6%  $  11.00
             いまの価格では赤字（利益率 -33.6%）。$19.19 まで上げるか、出品を止める
[止める  ] 一番くじ フィギュア A賞        利益率  51.6%  $  30.00
             仕入元に在庫が無い。**出品を止める。**
```

**無在庫でいちばん高くつくのは「買えないものが売れること」**なので、
在庫切れを利益率より先に見ます。採算が良くても、買えないなら止めるしかありません。
次に高くつくのが**仕入元の値上げに気づかず据え置くこと**で、赤字のまま売れ続けます。

`listings.csv` の列：`sku` / `title` / `current_price_usd` /
`cost_incl_tax_jpy`（仕入元の**現在**価格）/ `weight_g` / 寸法 /
`available`（仕入元の在庫）/ `previous_cost_jpy`（前回の仕入価格）

### 一括出品の下書き

`write_mass_upload()` が、**スコアの高い順に枠の数だけ**書き出します。
価格は目標利益率から順算した値が入ります。
Shopeeの公式テンプレートは市場ごとに列名が違い xlsx で配布されるため、
ここで出すのは**中身のCSV**で、公式テンプレートに貼り付けて使う前提です
（列名を決め打ちすると、テンプレートが変わった瞬間に壊れます）。

## eBay と Shopee ── 同じ戦略でいいのか

**市場を分けるのは正しいが、戦略まで同じにすると外します。**
買い手が買う価格帯・商品が見つかる仕組み・失敗したときの罰が、構造的に違います。

| | eBay | Shopee |
|---|---|---|
| 主戦場の価格帯 | $200前後。中古・絶版・コレクター品 | **プチプラ帯。**新品の消耗品・美容品 |
| 売れるもの | 一点物。同じ物が二度と入らない | **リピート品。**同じ物を繰り返し仕入れる |
| 見つかる仕組み | **検索。**だから競合出品数が意味を持つ | **キャンペーンとメガセール** |
| 競合データ | Browse API で公開・個人可 | **公開の競合検索APIが無い**（自店舗用のみ） |
| 配送 | 自分で国際発送 | **SLS。**セラー負担は国内送料だけ |
| 関税 | **セラー負担（DDP）** | **原則購入者負担** |
| 失敗の罰 | Below Standard で**手数料+6ポイント** | ペナルティポイントで**露出とメガセール参加資格**を失う |

### 3つの軸のうち、そのまま移せるのは2つ

**軸1は移りません。** 「競合が少ない型番を探す」がShopeeで成立しない理由は2つ。

1. 公開の競合検索APIが無いので、そもそも数字が取れない
2. もっと本質的に、**Shopeeの流入はキャンペーン駆動なので「誰も出していない」は
   「誰にも見つけられない」を意味します。** eBayなら検索から拾われますが、
   Shopeeでは流入そのものが起きません

**軸2は移ります。むしろ相性が良い。** リピート品なので、当たった商品は繰り返し仕入れられます。
ただし**在庫切れの罰がeBayより重い**ので、無在庫のまま引っ張るのは危険です。

**セット販売はよく移ります。** 低単価市場なので、送料が1回で済む効果が最大化されます。
同じ5点の構成で、米国 −1.8%→20.6%、Shopee 40.5%→51.0%。

### Shopeeで代わりに効く軸

- **ペナルティポイントを0に保つ**（3点超で検索順位が落ち、6点超で露出が絞られ、15点で停止）
- **メガセール（9.9 / 10.10 / 11.11 / 12.12）に合わせて在庫を積む**
- **チャットの応答速度**（返信の遅れがペナルティに繋がる）
- **1か国ずつ広げる**（台湾 → シンガポール → マレーシア）

### ツールの計算に反映していること

市場をShopeeに切り替えると自動で変わります。

| | 変えていること | 理由 |
|---|---|---|
| 下限価格 | eBay $30 → **Shopee $8** | eBayの下限を当てるとShopeeの売れ筋がほぼ全部「低単価」で落ちる |
| 配送手段 | **SLSを既定にする** | 自分で国際発送しないので、選べない手段で採算を出さないため |
| 地帯 | **台湾は第1地帯** | 東南アジア（第2地帯）より送料が安い。国を分けたのはこの差のため |
| 注文ごと固定費 | **0** | eBayの出品手数料に相当するものが無い |
| 在庫切れ警告 | 文言を市場ごとに変える | eBayは「手数料が上がる」、Shopeeは**「露出が絞られて売上がゼロになる」** |

```bash
python -m blueocean.cli --market shopee_tw margin --price 25 --cost 1200 \
    --weight-g 250 --length-cm 18 --width-cm 12 --height-cm 6
```

### 送料の負担は eBay と逆（当初モデルを取り違えていました）

| 費目 | eBay（米国・DDP） | Shopee（SLS） |
|---|---|---|
| 国内送料（集荷場所まで） | — | **セラー負担** |
| 国際送料 | **セラー負担** | SLSが処理 |
| ラストマイル配送 | （国際送料に含む） | SLSが処理 |
| 関税・通関 | **セラー負担（DDP）** | **原則購入者負担** |

**Shopeeでセラーが負担するのは国内送料だけです。**
当初これを国際送料にしていたため、**プチプラ商品がすべて赤字に見えていました。**
国内送料は重量ではなく**三辺計のサイズ区分**で決まり、月100件規模から佐川急便の集荷、
**800件規模でSPSの国内集荷料が無料**になるので、数が出れば**この費用自体が消えます**。

第1地帯（台湾）のEMS料金表は、確認できたアンカーが無いため第2地帯からの推定値です。
自分で郵便を使う場合は公式料金表で確認してください。

## 軸2のデータ ── eBayのレポートをそのまま入れる

軸2に要る列（`sku` / `listed_on` / `observed_on` / `views` / `watchers` / `sold`）は、
**Seller Hub の「All active listings」レポートに全部入っています。**
手で詰め替える作業は本来いりません。

### 取り方

1. [Seller Hub](https://www.ebay.com/sh/ovw) → **Reports** タブ
2. 左メニューの **Downloads** → **Download report**
3. Report source に **Listings**、Report type に **All active listings**
4. **Download**

### 取り込み

```bash
python -m blueocean.cli ingest \
```

## 抽出条件を保存して、毎回同じ条件で回す

抽出をそのつどコマンドで打っていると、次の3つが起きます。

- **どんな条件で抜いたのか、次に思い出せない**
- **条件を1文字変えるだけで、前回と比較できなくなる**
- 週次で回そうとすると、長いコマンドを毎回組み立てることになる

条件をファイルに固定すれば、3つとも同時に消えます。
**同じ条件で回すからこそ、前回との差分が意味を持ちます。**

```json
{
  "anime-set": {
    "label": "アニメ・フィギュアのまとめ売り",
    "market": "ebay_us",
    "target_margin": 0.20,
    "scan": {
      "genre": "anime_figure", "mode": "set", "limit": 40,
      "assume": {"weight_g": 1100, "length_cm": 32, "width_cm": 24, "height_cm": 18},
      "out": "out/anime-candidates.csv",
      "sheet": "out/anime-hunt.html"
    },
    "judge": {
      "candidates": "data/anime.csv", "history": "data/history.jsonl",
      "refresh": true, "out": "out/anime-plan.csv", "sheet": "out/anime-plan.html"
    }
  }
}
```

`scan` が「何を探すか」を決める工程、`judge` が「買っていいか」を決める工程です。
片方だけでも構いません。両方あるときは scan → judge の順に走ります。

```bash
python -m blueocean.cli job --config data/jobs.json --list        # 一覧
python -m blueocean.cli job --config data/jobs.json --name anime-set
python -m blueocean.cli job --config data/jobs.json --all         # 全部回す
```

```
=== オールドレンズ（週次の見直し）（lens-weekly）===
  条件: ebay_us / セラーレベル above_standard / 目標利益率 20% / 為替 150円

  [鮮度の警告] 前回の取得から 14日 経っています（2026-08-09）。

  走査 6件 → 探す価値あり 6件
  判定 8件 → 出品対象 4件

  前回からの変化 2件（うち要対応 1件）
    [判定悪化] LENS-002     BLUE → RED（2026-08-09 → 2026-08-23）

  書き出し: out/lens-hunt.html
  書き出し: out/lens-plan.csv
  書き出し: out/lens-plan.html
```

**2回目からは前回からの変化だけが出ます。** 週次で同じジョブを回すのが想定した使い方です。

**設定の綴り違いはエラーにします。** 黙って既定値で走らせると、
意図と違う条件で抽出し続けることになるためです（`target_margins` のような誤りを弾きます）。

### 抽出条件は何を指定するのか

| 条件 | 意味 |
|---|---|
| `scan.genre` / `keywords_file` | **抽出元。**ジャンルはシリーズ×形態に展開されます |
| `scan.mode` | `single`（単品）／`set`（まとめ売り）／`both` |
| `scan.assume` | **荷姿の仮定。**現物が手元に無い段階なので、重量と寸法を仮定して送料＝予算を出します |
| `market` / `target_margin` / `fx_jpy_per_usd` / `level` / `taxable` | 採算の前提 |
| `judge.refresh` | **CSVに値があってもeBay側を取り直す。**定期実行では必須 |
| `judge.history` | 履歴の追記先。前回との差分はここから出ます |

絞り込みの閾値（競合5件以下＝空き／30件以上＝過密／相場$30未満＝低単価で除外）は
`ScoringPolicy` の既定値です。

### ブラウザ版でできること

**抽出そのもの（eBayを検索して候補を作る工程）はブラウザ版ではできません。**
eBayのAPIを呼ぶ必要があり、あの画面は外部への通信をしない設計だからです。

代わりに軸1タブの「**抽出条件をつくる**」で条件を組み立てると、
**そのまま使える `jobs.json` と実行コマンドを出します。**
出力がPython版でそのまま読めることは確認済みです。

## 商品の写真 ── 探しに行く前に見た目を確かめる

**型番が同じでも、世代違い・マイナーチェンジ違いがあります。**
型番だけを頼りに国内を回ると、違うものを掴みます。買ってから気づいたのでは遅い。
とくに**セット販売は「何が入っているか」で値段が決まる**ので、写真が要ります。

### 照合シート（Python版）

`--sheet` を付けると、**eBayの商品写真つきの一覧（HTML）**を書き出します。
印刷して持って行くか、スマホで開いて店頭で照合する使い方です。

```bash
# 走査した型番を、写真つきで一覧にする
python -m blueocean.cli scan --keywords data/keywords.sample.txt --sheet hunt.html \
    --ebay-client-id "$EBAY_CLIENT_ID" --ebay-client-secret "$EBAY_CLIENT_SECRET"

# 判定した候補を、写真つきで一覧にする
python -m blueocean.cli axis1 --candidates data/candidates.csv --sheet plan.html
```

カード1枚に「商品写真6枚 / 予算 / eBay相場と競合数 / 判定理由 / eBayで見るリンク」が載ります。
**予算を先頭に置いてあります** ── 店頭で見るのはそこだけなので。

写真は eBay の出品画像を参照します。**ダウンロードして再配布はしません**（他人の出品写真なので）、
手元で開く1枚のHTMLから参照するだけです。

### ブラウザ版

**ブラウザ版にはeBayの写真を表示できません。** 公開ページは外部サイトへの画像リクエストを
遮断する仕組みの上で動いているためです。隠さずに、代わりの導線を2つ用意しました。

| | 何ができるか |
|---|---|
| **eBayへのリンク** | 各カードの「出品中の写真を見る ↗」「落札済みの写真と価格 ↗」から検索結果を開けます。実物の写真と、実際に売れた価格がそこで見られます |
| **自分で撮った写真** | 「1件だけ判定」「セット販売」で手元の写真を貼れます。端末内で240pxに縮小し、**この端末にだけ**保存します（サーバーには送りません） |

セットの構成品を撮っておくと、出品文を書くときにそのまま使えます。

## 値決め ── 仕入れた後に毎日ぶつかる問い

ここまでは「買っていいか」までしか答えていませんでした。
実際に毎日発生するのは、その次に来る問いのほうです。

| 問い | なぜ既存の機能では答えられなかったか |
|---|---|
| いくらで出せばいい？ | 仕入上限の逆算とは**向きが逆**。順算の口が無かった |
| Best Offer が来た。受ける？ | 越境ECでは毎日来る。**その場で返事が要る** |
| 円安が止まった。まだ黒字？ | 為替は全出品の採算を同時に動かす |
| 関税がまた上がったら？ | この半年で3回変わっている |
| 返品された。いくら損した？ | **往復送料**が効くので国内とは桁が違う |

どれも既存の利益計算式の変形で出せるのに、出していませんでした。

```bash
python -m blueocean.cli price --cost 9800 \
    --weight-g 180 --length-cm 16 --width-cm 12 --height-cm 10
```

```
=== 値決め（仕入 9,800円 / ebay_us）===

送料 2,299円（epacket / 課金重量 180g） / 為替 150円

  出品価格              $154.45（目標利益率 20%）

--- Best Offer をどこまで受けられるか ---

利益率      受諾価格      手取り    値引き
20%          $154.45     4,634円        0%
15%          $140.28     3,156円        9%
10%          $128.49     1,927円       17%
5%           $118.53       889円       23%
0%           $110.01         0円       29%

  出品時にこの表を控えておくと、Best Offer にその場で返事ができます。

--- どこまで環境が悪化しても耐えられるか ---

  為替    106.8円/USD を下回ると赤字（いま 150円。あと 43.2円の余裕）
  関税    32.5% を超えると赤字（いま 12.5%。あと 20.0ポイントの余裕）

--- 返品されたら ---

  1件あたりの損失      4,858円（往復の送料＋梱包＋注文ごと固定費）
  売れた1件の利益      4,634円
  許容できる返品率      48.8%（2.0件に1件まで）
```

**この最後の3行が、越境ECでいちばん見落とされるところです。**
返品1件の損失（4,858円）が、売れた1件の利益（4,634円）とほぼ同じ。
つまり**2件に1件返品されたら利益はゼロ**になります。
往復の国際送料が丸ごと損失になるためで、国内転売の感覚とは桁が違います。

返品1件が売上2件分以上の利益を食う出品には警告を出します。
そういう商品は値下げより先に、**説明文と状態表記を厚くして返品そのものを減らすほうが効きます。**

前提は次のとおりです（`--buyer-pays-return` / `--item-lost` で切り替え）。

- 落札手数料は返金時に戻る（eBayの原則）。注文ごと固定費は戻らない扱い
- 商品は手元に戻る＝原価は在庫として残る。戻らない（紛失・破損）場合は原価も損失に入る
- バイヤーが返送料を負担しても、**出した分の送料は戻らない**

## セット販売（まとめ売り）の採算

補論の「軸5：セット化・キュレーションで比較不能にする」を、数字で判断できるようにしたものです。

**セット化が効く理由は「比較されない」だけではありません。原価構造が変わります。**

| | 個別に5点売る | セットで売る |
|---|---|---|
| 注文 | 5件 | 1件 |
| 送料 | 5回 | **1回**（重量は合算される） |
| 注文ごと固定費 | 5回 | 1回 |
| 梱包 | 5回 | 1回 |

**送料が1回で済むのが最大の効き目**で、これは単価の低い商品ほど効きます。
そしてもう一つ大きいのが**死に筋の処理**です。単品では売れない在庫を売れ筋に混ぜると、
その時点で原価の回収が始まります。

```bash
python -m blueocean.cli bundle --items data/bundle.sample.csv --set-price 110 \
    --pack-weight-g 1100 --pack-length-cm 32 --pack-width-cm 24 --pack-height-cm 18
```

```
=== セット販売の採算（5点 / ebay_us）===

構成品                                  仕入    重量   単品相場
ねんどろいど（箱難あり）              1,800円   150g   $     45
figma（箱難あり）                     1,500円   150g   $     38
一番くじ フィギュア                     900円   300g   $     32
アクリルスタンド 3点                    500円    60g       単品不可
クリアファイル・缶バッジ 詰め合わせ      300円   120g       単品不可

               注文件数       売上     手数料       関税       送料       梱包       仕入 消費税還付       利益     利益率
個別に売る            3     17,250     -3,285     -2,156     -6,897       -600     -5,000        382       -306      -1.8%
セットで売る          1     16,500     -3,030     -2,062     -3,262       -200     -5,000        455      3,400      20.6%

  セットにすると利益が ＋3,706円
  損益分岐のセット売価  $74（これを下回るならセットにする意味がない）
  単品売価の合計        $115（いまの $110 は +4% の割引）
  判定                  セットにする価値あり
```

**この5点は、個別に売ると赤字（−1.8%）です。** 単価が低いので送料と手数料に食われ、
さらに2点は単品では売れずに在庫として残る。**同じ5点をセットにすると +20.6% になります。**
差を作っているのは主に送料で、3回分（6,897円）が1回分（3,262円）になっています。

市場を変えるとこうなります（同じ構成品・同じ$110）。

| 市場 | 個別に売る | セットで売る | 損益分岐 | 送料の節約 |
|---|---|---|---|---|
| eBay 米国 | **−306円（−1.8%）** | **+3,400円（20.6%）** | $74 | 3,635円 |
| eBay 欧州 | +3,137円（18.2%） | +5,997円（36.3%） | $87 | 2,882円 |
| Shopee 東南アジア | +6,983円（40.5%） | +8,415円（51.0%） | $100 | 1,569円 |

**関税と送料が重い市場ほど、セット化の効き目が大きい**ことが分かります。

### 出力の読み方

| 数字 | 意味 |
|---|---|
| **損益分岐のセット売価** | 個別売却と同じ利益を出すのに必要な価格。**これを下回るならセットにする意味がない** |
| 単品売価の合計 | 割引前の上限の目安。買い手はまとめ買いに割引を期待するので、これを超える値付けでは動かない |
| 送料の節約 | 個別の送料合計 − セットの送料 |

### セットが不利になる場合

無条件に有利ではありません。ツールは次を必ず警告します。

- **重量が合算されて送料の段が上がる。** 節約が目減りする、あるいは消えることがあります
- **束ねた結果が料金表の範囲を超える。** この場合ツールは固定値に落ちますが、
  **黙って固定値を使うと重いセットほど送料が安く見えてしまう**ので、落ちたことを明示します
- **まとめ売りは箱が大きくなり容積重量で課金されやすい。** 寸法の実測値を入れてください
- **セットは価格比較されない代わりに、検索にもかかりにくい。**
  だから軸2（出品後の反応を見る）が単品以上に重要になります

### 構成品CSV

```csv
name,cost_incl_tax_jpy,weight_g,length_cm,width_cm,height_cm,solo_price_usd
ねんどろいど（箱難あり）,1800,150,10,10,10,45
アクリルスタンド 3点,500,60,15,10,2,
```

**`solo_price_usd` を空にすると「単品では売れない見込み」**として扱います。
売上は立たず原価だけが残る計算になるので、死に筋を混ぜる効果が正しく出ます。
ここを「いつか売れる」と数えると、セット化の効果を過小評価します。

## データの更新

**軸1と軸2の判定ロジックは変えていません。変えたのは、そこに流し込むデータの扱いです。**

軸1が見ている数字は、放っておいても勝手に動きます。

| 動くもの | どう動くか | 影響 |
|---|---|---|
| 競合出品数 | 誰かが同じ商品を出せば増える | 数日で `BLUE` が `RED` に変わる |
| 相場 | 下がれば仕入上限が下がる | 昨日まで買えた仕入値が今日は採算割れ |
| 為替・関税・送料 | 全候補の採算が同時に動く | 判定が一斉にずれる |
| 国内在庫 | 売れて消える | 候補そのものが無くなる |

つまり**判定結果には賞味期限があります。** 一発判定を繰り返すだけでは、その賞味期限も
前回からの変化も見えません。**変化こそが行動のトリガー**なので、そこを持たないと
「毎回全件を人間が読み直す」運用になってしまいます。

### 軸1：履歴を持たせて、変化だけを読む

```bash
python -m blueocean.cli axis1 \
    --candidates data/candidates.csv \
    --history data/history.jsonl \
    --refresh \
    --ebay-client-id "$EBAY_CLIENT_ID" --ebay-client-secret "$EBAY_CLIENT_SECRET"
```

```
[鮮度の警告] 前回の取得から 14日 経っています（2026-08-09）。競合数と相場は日々動きます。

=== 前回からの変化（6件 / うち要対応 3件）===

[判定悪化] LENS-002     BLUE → RED（2026-08-09 → 2026-08-23）
             → 出品中なら価格と在庫を見直す。未出品なら見送りに回す
[採算割れ] PEN-001      仕入上限 26,000円 → 21,688円。仕入 24,000円 が上限を超えた
             → 相場・為替・送料のどれかが動いた。仕入値を下げられないなら見送る
[競合変動] LENS-002     競合 2件 → 34件（+1600%）
             → 増えているなら早く出す。値下げ競争が始まる前が勝負
[相場変動] VINYL-001    相場 $190 → $140（-26%）
[候補消滅] AMP-001      今回の候補リストに無い（前回 2026-08-09 は EXCLUDE）
```

要対応（判定悪化・採算割れ・判定改善・採算回復）が先に並びます。人間は上から読むので、
**手を打つべきものが上に来る**ようにしてあります。

| オプション | 用途 |
|---|---|
| `--history PATH` | 履歴JSONL。前回との差分を出し、今回の結果を**追記**する |
| `--refresh` | CSVに値があってもeBay側を取り直す。**定期更新はこれを付ける** |
| `--changes-only` | 変化だけを表示し、全件の判定は省く（毎週の確認用） |
| `--no-record` | 履歴に書かずに差分だけ見る（試算用） |

**`--refresh` が必要な理由。** 既定では、CSVに競合数と相場の両方が入っている候補には
問い合わせません（API未契約でも手動調査の値で動かせるようにするためです）。
ただしこの挙動には落とし穴があって、**一度手で埋めた値は放っておくと二度と更新されません。**
古い数字のまま `BLUE` と表示され続けることになります。`--refresh` はこれを打ち消します。

履歴は**追記のみ**で、既存の行を書き換えません。途中でツールが落ちても過去の履歴は壊れません。
また同じ日に2回走らせても「前回」は前の実行日のままなので、再実行で差分が消えることもありません。

推移を見るコマンドもあります。

```bash
python -m blueocean.cli history --history data/history.jsonl --sku LENS-002
```

```
=== LENS-002 の推移（3件）===

日付         判定     競合     相場   仕入上限  利益率
2026-08-09   BLUE        2 $    185     12,295   28.2%
2026-08-16   PROBE      12 $    180     11,887   27.0%
2026-08-23   RED        34 $    165     10,662   23.2%
```

**競合が増えて相場が下がっていく過程が見えます。** 一発判定では最後の行しか見えません。

### 軸2：観測CSVは追記して育てる

観測CSVは**毎週の行を足していく**運用です。同じSKUの行が何本並んでも構いません。

```csv
sku,listed_on,observed_on,views,watchers,sold
LENS-002,2026-07-20,2026-08-16,118,3,0
LENS-002,2026-07-20,2026-08-23,142,5,1   ← 追記
```

ツールが**SKUごとに最新の1行だけを判定対象**にし、1つ前の行を前回比の計算に使います。

```
[PROMOTE] LENS-002   34日 / 閲覧 142 / ウォッチ  5 / 販売1
            1件 販売済み。需要が確定したので有在庫化し、ハンドリングを1〜2日に短縮する
            前回比（7日）: 閲覧 +24 / ウォッチ +2 / 販売 +1
[DROP   ] FIG-001   114日 / 閲覧  21 / ウォッチ  0 / 販売0
            114日間 無反応。出品を終了して枠を空ける
            前回（2026-08-16／7日前）から動きなし  ← 停滞
```

累計142件の閲覧が、先週+3件なのか+80件なのかで意味はまるで違います。
**判定ルール自体は累計値のまま変えていません**（前回比の有無で結論は変わりません）。
前回比は、同じ判定の中で優先順位を付けるための材料です。

### 前提値（関税・料金表）の更新

| データ | 更新方法 | 頻度 |
|---|---|---|
| 関税率 | `--duty` / `DEFAULT_PROFILES` を書き換える | 制度変更のたび（§下記） |
| 為替 | `--fx`（既定150円/USD） | 相場が5円以上動いたら |
| 送料の料金表 | `--rates data/rates.csv` | 郵便料金改定のたび |
| eBay手数料 | `--fee` / `DEFAULT_PROFILES` | 規約変更のたび |

## 商品リサーチはどこまで自動化されているか

**「リサーチ全体が自動」ではありません。** 工程ごとに分けると次のとおりです。

| 工程 | 自動化 | 実装 | なぜそうなっているか |
|---|---|---|---|
| ⓪ **何を探すか**を決める | **自動** | `discovery.py` | eBayに出ていない型番を走査で特定する（`scan`） |
| ① 国内で**現物を見つける** | **手動** | なし | メルカリ・ヤフオク等のスクレイピングは規約に反しうるため、既定にしない |
| ② eBayの**競合出品数・相場**を取る | **自動** | `sources/ebay_browse.py` | Browse APIは個人でも使える |
| ③ 落札実績（何が売れたか）を取る | **不可** | — | Marketplace Insights APIが主要パートナー限定。**軸2が代替する** |
| ④ 送料を重量・寸法から出す | **自動** | `shipping.py` | 課金重量・階段料金・手段比較まで計算する |
| ⑤ 採算と競合から**判定する** | **自動** | `scoring.py` | ここがツールの本体 |
| ⑥ 出品する | **対象外** | — | 既存の出品ツール（SAATS等）が担当 |
| ⑦ 出品後の反応から次の一手を決める | **自動** | `promotion.py` | Seller HubのCSVを読む |

**自動化されていないのは①（国内で現物を見つける）だけです。**
それも「あてもなく眺める」ではなく、`scan` が出した**型番リストを持って探す**形になります。
①を手作業に残しているのは技術的な理由ではなく、**規約上の判断**です（上記「国内モールのAPI」参照）。
正規のデータ提供が使える仕入元が見つかれば、`blueocean/sources/` に
アダプタを足すだけで①も自動化できます（そのための抽象は `sources/base.py` に用意済み）。

**ブラウザ版にはAPI連携がありません。** 通信を一切しない設計なので、②は手入力になります。
API連携が要る運用はPython版を使ってください。

### 元データの制約

| データ | 取得方法 | 備考 |
|---|---|---|
| 競合出品数・価格帯 | **eBay Browse API** | 個人の開発者アカウントで利用可 |
| 落札実績 | Marketplace Insights API | **主要パートナー以外は不可** |
| 出品後の反応 | eBay Seller Hub のレポート | CSVでエクスポートして読み込む |
| 国内の仕入候補 | **手動CSV**（既定） | スクレイピングは規約違反になりうるため自動化しない |
| 国際送料の料金表 | **公式料金表を手動で投入** | 既定値は推定を含む。`--rates` で差し替える |
| 過去の判定 | **履歴JSONL**（`--history`） | ツールが自分で追記する。前回との差分の材料 |

**国内ECのスクレイピングは実装していません。** メルカリ・ヤフオクは規約で
「手元にない商品の出品」やデータの自動取得を制限しており、規約に適合しない取得手段を
既定にすべきではないと判断したためです。公式APIや正規のデータ提供が使える場合のみ、
`blueocean/sources/` にアダプタを追加してください。

**認証情報が無い場合は `MockSource` が使われます。** 決定的な擬似データを返すだけなので、
パイプラインの動作確認には使えますが、**判断には絶対に使わないでください**（実行時に警告を出します）。

### eBay Browse API を使う場合

```bash
python -m blueocean.cli axis1 \
    --candidates data/candidates.csv \
    --ebay-client-id "$EBAY_CLIENT_ID" \
    --ebay-client-secret "$EBAY_CLIENT_SECRET" \
    --out plan.csv
```

CSVに `market_price_usd` と `competitor_count` の両方を書いておけば、APIを呼びません。
API未契約の期間は、Terapeak等で手動調査した値を入れて運用できます。

## 設定できる前提

**関税率は流動的です。** 米国の制度はこの半年で3回変わりました（de minimis廃止 →
最高裁の違法判決 → 通商法122条 → 301条）。`blueocean/profit.py` の `DEFAULT_PROFILES`
は2026年8月時点の値なので、**運用前に必ず現在の値を確認して上書きしてください。**

```python
from blueocean.models import FeeProfile, Market
from blueocean.profit import DEFAULT_PROFILES

DEFAULT_PROFILES[Market.EBAY_US] = FeeProfile(
    market=Market.EBAY_US,
    fee_rate=0.18,        # eBay手数料の実効値
    per_order_fee_jpy=60,
    duty_rate=0.125,      # ← ここを最新の値に
    shipping_jpy=3000,    # 重量・寸法を渡さない場合のフォールバック値
    packaging_jpy=200,
)
```

**`shipping_jpy` は概算のフォールバックです。** 重量・寸法を渡せば `shipping.py` が
実際の課金重量から送料を出し、この値は使われません。

## このツールがやらないこと

- **出品そのもの** — SAATS Commerce等の既存ツールが担当します。本ツールは出品候補CSVを渡すところまで
- **国内ECの自動巡回** — 規約上の理由（上記）
- **落札実績の取得** — API制約（上記）。軸2が代替します
- **国内で現物を自動で見つけること** — 規約上の理由（上記）。何を探すかは `scan` が決めます
- **送料の実額の保証** — 料金表は推定を含みます。公式料金表で差し替える前提です
- **定期実行そのもの** — `--history` を付けて走らせる仕組み（cron等）は各自の環境で組んでください

**既存の出品ツールと競合しません。** 既存ツールが持っていない「判断」の部分だけを埋めます。
