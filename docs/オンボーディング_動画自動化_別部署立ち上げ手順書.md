# 動画自動化パイプライン オンボーディング手順書（別部署 新規立ち上げ版）

> **目的**：既存の「シナリオ作成 → 動画生成 → YouTube予約投稿」の全自動パイプラインを、**別部署が新しいYouTubeチャンネル・新しい認証でゼロから**立ち上げ、そのままコピーして即運用できるようにするための手順書＋知見集です。
>
> **対象**：長尺パイプライン（`pipeline/`）＋ショートパイプライン（`video-automation/`）の両方。
>
> **前提**：Claude Code on the web（クラウド実行環境）を使い、毎日決まった時刻に「まっさらな新セッション」で全自動実行します。

---

## 0. 全体像（まず読む・5分）

### 0-1. 2本のパイプライン

| | 長尺パイプライン | ショートパイプライン |
|---|---|---|
| リポジトリ | `todoapp_1`（`pipeline/`配下） | `video-automation`（`generator/`配下） |
| 尺 | 8〜15分の横型（1920×1080） | 60秒以内の縦型（1080×1920） |
| 台本生成 | OpenAI `gpt-4o`（章立て→章展開の多段生成） | Anthropic Claude `haiku`（1回でJSON台本） |
| 音声(TTS) | Google Cloud TTS（`ja-JP-Neural2-B`） | OpenAI TTS（`gpt-4o-mini-tts`, voice=nova） |
| 画像 | Stability AI（16:9, 約30枚） | Stability AI（9:16, 2枚） |
| 合成 | ffmpeg（Ken Burns＋焼き込み字幕） | moviepy（imageio-ffmpeg同梱） |
| 投稿 | YouTube Data API v3（private＋publishAt予約） | 同左 |

### 0-2. 設計思想（これを外すと壊れる）

1. **毎回まっさらな新セッションで実行される**。作業ディレクトリにコードは無い前提。トリガーのプロンプト冒頭で**必ず自分でgit cloneする**。
2. **状態ファイルに依存しない**。ネタ被り回避は「YouTube上の直近タイトル」を都度取得して行う（`fetch_recent_titles()`）。ローカルの履歴ファイルはクローンのたびに消えるため信用しない。
3. **秘密情報はすべて環境変数**。コードにキー・トークンを一切ハードコードしない。ログにも出さない。
4. **環境変数は「新規セッション」にのみ反映される**。既存セッションに後から入れた値は伝わらない。→ トークン更新後の検証は必ず**新セッション**で行う（後述の鉄則）。
5. **予約投稿は `private` + `publishAt`**。YouTubeが指定時刻に自動公開する。生成失敗時はダミーで“成功に見せかけない”＝中断してエラーを報告。

## 1. アカウント・認証の準備（ここが山場）

別部署は**新しいチャンネル・新しい認証**で立ち上げるため、この章を最初に完了させます。所要 30〜60分。

### 1-1. YouTubeチャンネルを用意
- 投稿先の Google アカウントで YouTube チャンネルを作成（ブランドアカウント推奨）。
- このアカウントで以降のOAuth認可を行う。**認可するGoogleアカウント＝投稿先チャンネルの持ち主**であること。

### 1-2. Google Cloud プロジェクトでAPIを有効化
[Google Cloud Console](https://console.cloud.google.com/) で新規プロジェクトを作り、**APIとサービス → ライブラリ**で次を「有効にする」：
- **YouTube Data API v3**（アップロード・タイトル取得）
- **YouTube Analytics API**（週次レポート用。任意だが推奨）
- **Cloud Text-to-Speech API**（長尺の音声。APIキー方式で使う）

### 1-3. OAuth同意画面（★invalid_grant を防ぐ最重要設定）
**APIとサービス → OAuth同意画面**：
1. User Type = **External** で作成。
2. アプリ名・サポートメール・デベロッパー連絡先を入力。
3. **スコープを追加**：
   - `.../auth/youtube.upload`
   - `.../auth/youtube`
   - `.../auth/yt-analytics.readonly`（分析を使う場合）
4. **公開ステータスを「本番（In production）」に "公開"する**。
   - ⚠️ **「テスト中(Testing)」のままだと refresh token が7日で失効し `invalid_grant` になる**。ここを本番公開にするのが最重要。

### 1-4. OAuthクライアント（Playground用）を作成
**APIとサービス → 認証情報 → 認証情報を作成 → OAuthクライアントID**：
- アプリケーションの種類 = **ウェブアプリケーション**
- **承認済みのリダイレクトURI**に次を追加：
  `https://developers.google.com/oauthplayground`
- 作成後に表示される **クライアントID** と **クライアントシークレット** を控える（＝`YOUTUBE_CLIENT_ID` / `YOUTUBE_CLIENT_SECRET`）。

### 1-5. リフレッシュトークンを発行（OAuth Playground）
[OAuth 2.0 Playground](https://developers.google.com/oauthplayground/) で：
1. 右上の **⚙（歯車）** → **「Use your own OAuth credentials」にチェック** → 1-4の**クライアントID/シークレットを貼る**。
2. 左の **Step 1** の「Input your own scopes」欄に、使うスコープを**URLのまま**入力（改行 or 半角スペース区切り）：
   ```
   https://www.googleapis.com/auth/youtube.upload
   https://www.googleapis.com/auth/youtube
   https://www.googleapis.com/auth/yt-analytics.readonly
   ```
   → **Authorize APIs** → **投稿先チャンネルのGoogleアカウント**でログイン → 許可。
3. **Step 2** → **Exchange authorization code for tokens** → 表示された **Refresh token** をコピー（＝`YOUTUBE_REFRESH_TOKEN`）。

#### ★3点一致の鉄則
`YOUTUBE_CLIENT_ID` / `YOUTUBE_CLIENT_SECRET` / `YOUTUBE_REFRESH_TOKEN` は、**必ず同じ1つのOAuthクライアントから発行された3つ**を使うこと。
- クライアントシークレットを作り直したり、別のクライアントのトークンを混在させると `unauthorized_client` になる。
- Playgroundで発行するときは必ず**⚙で自分のクライアントを指定してから**トークンを取る（これを忘れると Google 既定クライアントのトークンが出て、env の client_id と食い違う）。

### 1-6. その他のAPIキー
| 環境変数 | サービス | 用途 | 取得先 |
|---|---|---|---|
| `OPENAI_API_KEY` | OpenAI | 長尺の台本＋ショートのTTS | platform.openai.com |
| `STABILITY_API_KEY` | Stability AI | 画像・サムネ生成 | platform.stability.ai |
| `GOOGLE_TTS_API_KEY` | Google Cloud TTS | 長尺の音声（REST・APIキー方式） | Cloud Console → 認証情報 → APIキー |
| `PIPELINE_ANTHROPIC_KEY` | Anthropic | ショートの台本生成 | console.anthropic.com |
| `YOUTUBE_RESEARCH_API_KEY` | YouTube Data API | ジャンルリサーチ（検索集計） | Cloud Console → APIキー |

> Google TTS の APIキーは、Cloud Console で「APIキー」を作成し、**Cloud Text-to-Speech API に限定**しておくと安全。

### 1-7. 認証エラー早見表（詰まったらここ）
| エラー | 意味 | 対処 |
|---|---|---|
| `invalid_grant` | トークン失効/取消/時刻ズレ | 同意画面を**本番公開**にしてトークン再発行 |
| `unauthorized_client` | トークンとclient_id/secretの不一致 | ⚙で自分のクライアントを指定し、**3点を同一クライアントから**再取得 |
| `invalid_scope` | refresh時に付与と違うスコープを要求 | refreshでは`scopes`を渡さない（本コードは渡していない）。必要スコープでトークン再発行 |
| `invalid_client` | client_id/secretが誤り/削除済み | クライアントを確認・再作成 |
| `insufficient permissions`（コメント投稿403） | `youtube.force-ssl` 未付与 | 固定コメントはStudioで手動 or スコープ追加してトークン再発行 |

## 2. クラウド実行環境（Claude Code on the web）

### 2-1. 環境を作成し、Secrets/環境変数を登録
環境設定の **Secrets／環境変数** に、下記をすべて登録します。値は絶対にコード・ログ・チャットに出さないこと。

**長尺パイプライン用**
```
OPENAI_API_KEY=...
STABILITY_API_KEY=...
GOOGLE_TTS_API_KEY=...
YOUTUBE_CLIENT_ID=...
YOUTUBE_CLIENT_SECRET=...
YOUTUBE_REFRESH_TOKEN=...
# 任意（既定値あり）: TTS_PROVIDER=google / GOOGLE_TTS_VOICE=ja-JP-Neural2-B /
#                     GOOGLE_TTS_RATE=1.05 / SCRIPT_MODEL=gpt-4o / ROTATION_PHASE=1
```

**ショートパイプライン用（同一環境に追加でOK）**
```
PIPELINE_ANTHROPIC_KEY=...
YOUTUBE_RESEARCH_API_KEY=...
# OPENAI_API_KEY / STABILITY_API_KEY / YOUTUBE_* は長尺と共用
```

> 別部署は**別チャンネル＝別のYOUTUBE_\* 3点**になる。長尺とショートを同じチャンネルに出すなら3点は共用、別チャンネルなら別の環境（または別の変数運用）に分ける。

### 2-2. ネットワーク許可（Custom allowlist）
アウトバウンドを制限している場合、次のドメインを許可：
```
api.openai.com
api.stability.ai
texttospeech.googleapis.com
oauth2.googleapis.com
www.googleapis.com
youtube.googleapis.com
api.anthropic.com          # ショートの台本生成
github.com                 # リポジトリ clone（プロキシ経由で通ることが多い）
```
> パッケージ導入（apt/pip）で追加ドメインが要る場合あり。setup 実行時に落ちたら、その先のドメインを許可に足す。

### 2-3. 環境変数の反映タイミング（重要）
- 環境変数の追加・変更は**新しく起動するセッションにだけ反映**される。
- したがって**トークンを更新したら、必ず“新セッション”で検証**する（→ 6章の鉄則）。

## 3. リポジトリの準備

### 3-1. コードを別部署用に複製
- 既存の2リポジトリ（`todoapp_1`・`video-automation`）を**フォーク or 複製**し、別部署のリポジトリにする。

**長尺 `pipeline/config.py`**

## 4. パイプラインの中身（運用者が知っておくこと）

### 4-1. 長尺（`pipeline/run.py`）
```bash
# ジャンル指定して生成＋予約投稿
python3 run.py --genre space
# 日替わりで宇宙↔都市伝説を自動選択（状態ファイル不要）
python3 run.py --rotate-date
# 生成のみ（YouTubeに上げない）
python3 run.py --genre space --no-upload
# 認証だけ検証して終了（動画は作らない）
python3 run.py --check-auth
# 手書き台本から生成（初回シード等）
python3 run.py --genre mystery --intro-seed scripts/xxx.txt --intro-title "タイトル"
# 長尺の予告編ショート(縦型CM)も続けて生成・投稿
python3 run.py --genre mystery --teaser --intro-seed ... --intro-title ...
```
**処理段**：台本(OpenAI・章立て多段) → TTS(Google, 字幕単位で個別合成し実測秒で同期) → 画像(Stability) → ffmpeg合成(Ken Burns＋焼き込み字幕) → サムネ → アップロード(19〜20時JST予約)。

**字幕同期の知見**：字幕は「文字数比の推定」ではなく、**各字幕単位を個別にTTSして実測再生時間で表示区間を決める**（`tts.synthesize_timed()` → `assemble._srt_from_segments()`）。各行は「次の単位が始まるまで」表示し続け、早く消えない。フォントは本編26pt/縦型36pt、太い縁取りで可読性を確保。

### 4-2. ショート（`video-automation/generator/daily_routine.py`）
```bash
cd generator && python3 daily_routine.py   # POST_TIMES の各枠に1本ずつ生成・予約投稿
```
**処理段**：台本(Claude・JSON1発、冒頭3秒フック＋寸止めCTA) → 画像(Stability縦型2枚) → TTS(OpenAI) → moviepy合成(字幕) → アップロード。ネタ被りは「YouTube直近タイトル」＋「その日の既出台本全文」の二重で回避。

**広告運用の知見**：ショートは広告配信する前提で、**冒頭3秒フック**と**寸止めCTA（核心を見せきらず概要欄/固定コメントのリンクへ誘導）**を極限まで作り込む。長尺本編の“予告編（CM）”として、視聴と登録を本編に集約する導線。

## 5. トリガー（Routines）— 毎日の自動実行

Claude Code の Routine（cron）で、毎日フレッシュな新セッションを起動して実行します。

### 5-1. cronはUTC。JSTへの換算
- **cronはUTC**、最短は1時間毎。**JST = UTC + 9時間**。
- 「投稿時刻(publishAt)」より**数時間前に起動**する（生成に十数分〜30分、`next_publish_at`は最低3時間のリードを要求）。
- 例：`0 4 * * *`(UTC) = **13:00 JST起動** → 19:00 JST公開の長尺を生成。

### 5-2. トリガー・プロンプトの型（★そのままコピー、URLだけ差し替え）
```
これは毎日自動実行される動画生成・予約投稿タスクです。人間の確認は不要。全自動で最後まで完了させ、最後に必ず結果を報告してください。

【重要】このセッションはまっさらな新セッションで、作業ディレクトリにコードがありません。まず自分でリポジトリをクローンしてください（認証はプロキシ経由で通ります）。

【手順（この順序を厳守）】
1. リポジトリ取得:
   if [ -d ~/REPO/.git ]; then cd ~/REPO && git fetch origin BRANCH && git checkout BRANCH && git pull origin BRANCH; else git clone --branch BRANCH https://github.com/OWNER/REPO.git ~/REPO && cd ~/REPO; fi
   取得に失敗したら中断してgitエラーを報告。
2. 依存導入: cd ~/REPO && bash pipeline/setup.sh
3. ★先に認証を検証: cd ~/REPO/pipeline && python3 run.py --check-auth
   - 「[check-auth] OK」が出た場合のみ手順4へ。失敗なら動画を作らず中断し、エラー全文を報告。
4. 生成＋予約投稿: python3 run.py --rotate-date   （ショートは cd generator && python3 daily_routine.py）
5. 最後に必ず報告: 認証結果 / ジャンル / タイトル / 音声尺(分) / 予約公開時刻(JST) / 動画URL。失敗時は「どの工程で落ちたか＋エラー全文」。

【厳守】
- 鍵・トークンはこの環境に設定済み。値は絶対に表示しない。
- エラー時にダミー音声・プレースホルダ画像・別ジャンルへの安易な切替で「成功」に見せかけない。必ず中断して原因を具体的に報告する。
- 生成に十数分かかる。アップロード完了までセッションを終了しない。
```
`OWNER/REPO/BRANCH` を別部署の値に置換。ショート用は手順2・4のコマンドをショート側に差し替える。

### 5-3. 併設する定期ルーチン（推奨）
| ルーチン | 周期(例) | 役割 |
|---|---|---|
| 長尺 生成・予約投稿 | 毎日 | ジャンルローテーションで1本 |
| ショート 生成・予約投稿 | 毎日 | `POST_TIMES`の枠数だけ |
| 週次パフォーマンス集計 | 週1 | 再生数・視聴時間・登録者。**広告/ショート視聴を除いた“収益化算入オーガニック視聴時間”を必ず出す** |
| ジャンルリサーチ | 週1 | 上位ジャンルの入れ替わりを検知し台本ジャンル見直し |
| API残高チェック | 3日毎 | Stability残高・各キー有効性 |

## 6. 検証・運用の鉄則（過去の失敗から得た知見）

### 6-1. ★トークンは「新セッションの --check-auth」で検証してから“有効”と言う
- 自分の作業セッションでの読み取りテストだけで「有効」と判断しない。
- 環境変数は**新規セッションにのみ反映**されるため、トークン更新後は**新しいセッションを起動**して `python3 run.py --check-auth` を通し、`[check-auth] OK` と投稿先チャンネル名が出て初めて「有効」とする。
- `check-auth` は `channels.list` で**実際にトークンをリフレッシュ**するので、失効・client不一致・スコープ不足はここで必ず落ちる。トリガーにも「check-auth OK の時だけ生成へ進む」ゲートを必ず入れる。

### 6-2. 収益化の現実（正直な集計）
- 4,000時間の収益化条件に、**広告(ADVERTISING)経由・ショートフィード(SHORTS)経由の視聴時間は算入されない**。
- 週次では `insightTrafficSourceType` 次元で切り分け、**「広告・ショートを除いたオーガニック長尺の視聴時間」を最重要指標**として最初に出す。総再生時間だけを見て過大評価しない。
- インプレッション/CTRはこのチャンネル種別ではAPI非対応のことがある → Studioで確認する旨を添える。

### 6-3. 重複投稿の防止
- 移行日・スケジュール変更日は**トリガーの有効/無効**と**リマインダー**を使い、同日二重生成を避ける。
- 生成本数を変える日は、前日夜のうちに翌日の初回起動を1回だけにする等の調整をする。

### 6-4. よくある失敗と対処
| 症状 | 原因 | 対処 |
|---|---|---|
| 新セッションで「コードが無い」 | クローン手順漏れ | トリガー冒頭のclone手順を必ず入れる |
| YouTube認証が本番で落ちる | 同意画面がTesting/トークン失効 | 本番公開＋新セッションでcheck-auth |
| 初回だけauthコケる | `cffi`未導入 | `requirements.txt`に`cffi`をピン（導入済み） |
| TTS/画像が瞬断で落ちる | 一時的5xx/接続断 | `http_retry.request_with_retry`（指数バックオフ）で吸収済み |
| 字幕が音声より早く消える | 文字数比の推定 | `synthesize_timed`＋実測SRTで同期（対応済み） |
| 予約が過去時刻で拒否 | リードタイム不足 | `next_publish_at`が最低3時間先に自動補正 |

### 6-5. セキュリティ・運用ルール（厳守）
- **APIキー・リフレッシュトークンの値を、コード・ログ・PR・チャット・コミットに一切出さない**。
- 本番`main`への直接pushはしない（PR経由）。作業は指定の開発ブランチで。
- 生成失敗時に**ダミーで成功に見せかけない**。中断して原因を報告する。
